# Keys

From M1-09 on, the firmware has the key engine that decides which key and modifier reports go out. A tap on a modifier applies it to the next key, a double tap locks it, and a tap on a locked one turns it off. No key or modifier is ever left down, because every key goes out with its release in the same step and a modifier leaves only inside the report of the key it applies to. In milestone 1 the engine's only sink is the console key log, so nothing reaches the PC. A developer or the harness drives the engine over the debug console, watches each report as a `keys:` log line, and reads a record of up to 2048 reports back with `$TD serial keys`. M1-10 and M1-11 connect the pages to the same engine, and the post-product update adds the USB HID sink behind the same interface.

## Sub-features

- `keys-tap` answers `keys tap <usage>` by sending the key with every active modifier and then the all-released report, `kbd <mods> [<usage>]` then `kbd 0 []`, and returns one-shot modifiers to `OFF`. `<usage>` is a decimal keyboard usage from 1 to 255 or `F1` to `F24`, which map to 58 to 69 and 104 to 115.
- `keys-consumer` answers `keys consumer <usage>` by sending `con <usage>` then `con 0`, with no modifier, and leaves every modifier as it is.
- `keys-mod` answers `keys mod ctrl|shift|alt|win` with the modifier's new state. `OFF` goes to `ONE_SHOT`. A second tap within 300 ms goes to `LOCKED`. A tap on `ONE_SHOT` after 300 ms, or on `LOCKED`, goes to `OFF`. The HID modifier bits are Ctrl 1, Shift 2, Alt 4, Win 8.
- `keys-clear` answers `keys clear` by returning one-shot modifiers to `OFF` and keeping locked ones, and `keys clear all` by returning every modifier to `OFF`. Neither sends a report.
- `keys-state` answers `keys state` with the four modifier states, `seq`, the reports since boot, and whether the log and the record are on.
- `keys-log` answers `keys log on|off`. With the log on, each report prints `keys: {"seq":N,"t":T,"type":"kbd","mods":M,"keys":[...]}` or `keys: {"seq":N,"t":T,"type":"con","usage":U}`. `seq` counts reports from 1 since boot and `t` is milliseconds since boot. The log is off after boot.
- `keys-record` answers `keys record start`, which empties the record and starts it, and `keys record stop`, both with `recording`, `count`, and `dropped`. The record keeps 2048 reports in PSRAM and counts the ones that did not fit in `dropped`. `keys record dump` streams the record as a `start` reply, one `@tdr` line per report in the log line's JSON, and an `end` reply.
- `keys-fuzz` answers `keys fuzz <n> <seed>` by running `n` random events through the pure reducer with a checking sink of its own, so the engine on the board, the log, and the record see nothing, and replies with `events`, `reports`, `violations`, and `elapsed_us`. A violation is a step that left a key down or a report that carried a modifier with no key.
- `keys-errors` answers a wrong argument count, a usage outside its range, an unknown modifier or subcommand with a usage text and `ok` false.

## How to get to it (user POV)

- Open a serial terminal on the board's port and type `keys log on`, `keys mod shift`, `keys tap F15`, or `keys state` at `td> `.
- Run `$TD serial cmd "<line>"`, which sends the same line and prints the reply as JSON. Run `$TD serial capture --no-reset --send "<line>"` when the `keys:` log lines are the evidence. Run `$TD serial keys --out <file>` to read the record.
- Tap a tile on the F-Keys or Media page from M1-10 and M1-11 on. The page calls the engine, so the same `keys:` lines and record entries appear.

## Driving it with touchdeck.ps1

Preconditions:

- The build under test is M1-09 or later, and `$TD serial doctor` exits `0` with `build_matches` true.
- Evidence directory `E=<absolute path>/.verify/<YYYYMMDD-HHMMSS>-keys` is new, and Doctor's JSON is saved there as `doctor.json`.
- The modifiers start at `OFF` and the record is empty. Doctor's reset gives both. Between recipes, `$TD serial cmd "keys clear all"` returns the modifiers to `OFF` without a reset, and `keys record start` empties the record.
- A recipe that reads the record runs `$TD serial cmd "keys record start"` before its events, `$TD serial cmd "keys record stop"` after them, and then `$TD serial keys --out $E/<name>.json`. The `brief` list in that file writes each report as `kbd <mods> [<keys>]` or `con <usage>`, in order, so a recipe's expected record reads straight off it.

- **Key log.** Run `$TD serial capture --out $E/log --seconds 6 --no-reset --send "keys log on" --send "keys mod shift" --send "keys tap F15" --send "keys tap F16" --send "keys log off" --expect 'keys: \{"seq":\d+,"t":\d+,"type":"kbd","mods":2,"keys":\[106\]\}' --expect 'keys: \{"seq":\d+,"t":\d+,"type":"kbd","mods":0,"keys":\[\]\}' --expect 'keys: \{"seq":\d+,"t":\d+,"type":"kbd","mods":0,"keys":\[107\]\}' --expect 'keys: \{"seq":\d+,"t":\d+,"type":"kbd","mods":0,"keys":\[\]\}'`. Exit `0`. The four `keys:` lines come in that order, so Shift rode on F15 and not on F16. In PowerShell, `(Select-String -Path $E/log/serial.log -Pattern 'keys: \{').Count` prints 4. The log lines go through stdio, which a redrawing display can drop, so the record is the proof when a count matters.
- **One-shot modifier.** Start the record, run `$TD serial cmd "keys mod shift" > $E/one-shot-mod.json`, `$TD serial cmd "keys tap F15"`, `$TD serial cmd "keys tap F16"`, and `$TD serial cmd "keys state" > $E/one-shot-state.json`, stop the record, and run `$TD serial keys --out $E/one-shot.json`. Every command exits `0`. The `mod` reply has `"state":"ONE_SHOT"`. `brief` is exactly `kbd 2 [106]`, `kbd 0 []`, `kbd 0 [107]`, `kbd 0 []`, with `count` 4 and `dropped` 0. `keys state` reports `shift` `OFF`, because the key tap spent it.
- **Locked modifier.** Start the record, run `$TD serial cmd "keys mod ctrl" --repeat 2 > $E/lock-mod.jsonl`, then `keys tap F15`, `keys tap F16`, and `keys state > $E/lock-state.json`, stop the record, and run `$TD serial keys --out $E/lock.json`. The two `mod` replies read `ONE_SHOT` then `LOCKED`, and their `t` values are under 300 apart, which is the board's own clock. `brief` is `kbd 1 [106]`, `kbd 0 []`, `kbd 1 [107]`, `kbd 0 []`, and `keys state` reports `ctrl` `LOCKED`, because a locked modifier rides on every key. A `--repeat 2` pair lands about 10 ms apart. Should it ever read 300 or more, the second reply says `OFF` and the recipe is inconclusive, not failed, so run it again.
- **Unlock.** With Ctrl locked, start the record, run `$TD serial cmd "keys mod ctrl" > $E/unlock-mod.json` and `keys tap F15`, stop the record, and run `$TD serial keys --out $E/unlock.json`. The `mod` reply reads `OFF`, and `brief` is `kbd 0 [106]`, `kbd 0 []`.
- **Double-tap timing.** Run `$TD serial cmd "keys mod alt" --repeat 2 --interval 0.2 > $E/timing-fast.jsonl`, `$TD serial cmd "keys state" > $E/timing-fast-state.json`, `$TD serial cmd "keys clear all"`, `$TD serial cmd "keys mod alt" --repeat 2 --interval 0.4 > $E/timing-slow.jsonl`, and `$TD serial cmd "keys state" > $E/timing-slow-state.json`. The fast pair's `t` values are under 300 apart and leave `alt` `LOCKED`. The slow pair's are over 300 apart and leave `alt` `OFF`. Judge the gap by `t`, not by `--interval`, because the host adds its own time.
- **Two modifiers on one key.** Start the record, run `keys mod shift`, `keys mod ctrl`, and `keys tap F17`, read `keys state`, stop the record, and run `$TD serial keys --out $E/combo.json`. `brief` is `kbd 3 [108]`, `kbd 0 []`, and both modifiers read `OFF`.
- **Win never goes out alone.** Start the record, run `keys mod win` and `keys tap F13`, stop the record, and run `$TD serial keys --out $E/win.json`. `brief` is exactly `kbd 8 [104]`, `kbd 0 []`. No entry has `mods` above 0 with an empty `keys` list, which is the property the engine holds for every event.
- **Consumer keys leave a lock alone.** Lock Ctrl with `keys mod ctrl --repeat 2`, start the record, run `keys consumer 233` and `keys consumer 234`, read `keys state`, stop the record, and run `$TD serial keys --out $E/consumer.json`. `brief` is `con 233`, `con 0`, `con 234`, `con 0`, and `ctrl` still reads `LOCKED`.
- **Fuzz.** Start the record, run `$TD serial cmd "keys fuzz 10000 1" > $E/fuzz-1.json` and `$TD serial cmd "keys fuzz 10000 2" > $E/fuzz-2.json`, stop the record, and run `$TD serial keys --out $E/fuzz-record.json`. Both replies have `ok` true, `events` 10000, `violations` 0, and `reports` above 0, and the record has `count` 0, because the fuzz uses a state and a sink of its own. `elapsed_us` divided by `events` is the reducer's time per event on the board, with the checking sink included. Report it.
- **Burst.** Lock Shift, start the record, run `$TD serial cmd "keys tap F18" --repeat 500 > $E/burst.jsonl`, stop the record with `$TD serial cmd "keys record stop" > $E/burst-stop.json`, and run `$TD serial keys --out $E/burst.json`. `burst-stop.json` has `count` 1000 and `dropped` 0. In PowerShell, `$r = (Get-Content $E/burst.json | ConvertFrom-Json); ($r.brief | Select-Object -Index (0..999 | Where-Object { $_ % 2 -eq 0 }) | Where-Object { $_ -ne 'kbd 2 [109]' }).Count` prints 0, the same with odd indexes and `'kbd 0 []'` prints 0, and `(1..999 | Where-Object { $r.reports[$_].seq -ne $r.reports[$_ - 1].seq + 1 }).Count` prints 0, so `seq` rose by one per report.
- **Record full.** Lock nothing, start the record, run `$TD serial cmd "keys tap F13" --repeat 1030`, and stop the record with `$TD serial cmd "keys record stop" > $E/full-stop.json`. `count` is 2048 and `dropped` is 12, because 1030 taps make 2060 reports and the record holds 2048. `$TD serial keys --out $E/full.json` exits `0` with 2048 `brief` entries, the last one `kbd 0 []`.
- **Sink time.** With the log off, run `$TD serial cmd "keys tap F13" --repeat 100 --time > $E/sink.jsonl 2> $E/sink-rtt.txt`. In PowerShell, `$s = Get-Content $E/sink.jsonl | ForEach-Object { ($_ | ConvertFrom-Json).sink_us } | Sort-Object; $s[[int][math]::Ceiling(0.95 * $s.Count) - 1]` prints the p95 of `sink_us`, and the plan's bound is 1000. `rtt_ms` in `sink-rtt.txt` is the host's round trip, with a bound of 50. `sink_us` covers the reducer step and the two sink calls under the engine's lock. It leaves out the console line's parse before and the reply's trip after.
- **Reset clears everything.** Lock Ctrl, then run `$TD serial capture --out $E/reset --seconds 10 --no-reset --send "reboot" --expect "touchdeck: TouchDeck firmware starting" --expect 'keys: started, record holds 2048 reports'`. Exit `0`. Then `$TD serial cmd "keys state" > $E/after-reboot.json` reports every modifier `OFF`, `seq` 0, `log` false, and `recording` false.
- **Proof.** Keep `$E/doctor.json`, each capture's `serial.log` and `summary.json`, every `cmd` reply file, and every `$TD serial keys` output file. In milestone 1 nothing reaches the PC, so say so in the report. The record is the proof of what would have been sent.

## Gotchas

- Nothing reaches the PC in milestone 1. The key engine's only sink is the console key log. A `keys:` line or a record entry proves that the engine emitted the report, and a watcher on the PC would see nothing. The USB HID sink comes in the post-product update, behind the same interface.
- `keys record dump` streams and blocks the console until its `end` reply, like `screenshot`. Always read it with `$TD serial keys`. `cmd` returns the `start` reply and leaves the stream in flight, and the next command then races the stream.
- `keys log on` stays on until `keys log off` or a reset. Its lines go through stdio, which the display can drop while it redraws, so count reports in the record, not in the log, when the count matters.
- The record is not a ring. Once it holds 2048 reports it drops the rest and counts them. `keys record start` empties it. A recipe that expects a count starts the record itself.
- A reset returns every modifier to `OFF`, empties the record, turns the log off, and sets `seq` back to 0. The modifier states survive nothing else either: there is no storage.
- The double-tap window is 300 ms by the board's clock, which the `t` field of each `mod` reply reports. Judge a pair by the difference of the two `t` values. `--interval` sets the host's pause, and the console round trip adds about 10 ms to it.
- `keys fuzz` runs on the console task for `n` steps, under a microsecond each, so 100000 steps take well under a second and block the console meanwhile. The cap is 100000, which keeps the longest run clear of the idle task watchdog.
- A `keys tap` of usage 0 is refused by the console with a usage text, and so is a usage above 255. The engine itself emits nothing for either, so no path can send a modifier with no key.
- From M1-12 on, the idle screen-off clears every modifier, one-shot and locked alike, so a lock set more than the idle timeout before its key is gone, and the first tap on the dark screen sends nothing. Run `$TD serial cmd "power state"` first and wake the screen if it says `OFF`. [Idle](./idle.md) has the rules.
- `help` lists `keys` after `touch`. Take the argument forms from this file. `help` only confirms the name.
- The `t` field of a record entry or `mod` reply and the `I (ms)` stamp on a log line are two clocks. They differ by a constant that changes each boot, 292 ms on one M1-12 run. Compare times within one clock only. To line a record entry up with a log line, measure the offset on that boot first.
- The board lock. Only the holder of `.verify/hardware.lock` opens the port. `seq`, the modifier states, and the record are one set for the whole board, so another run's tap changes them.
