# F-Keys page

From M1-10 on, the `F-Keys` page of the deck sends keys. A tap on `F1` to `F12` sends that key through the key engine, and a tap on `Shift`, `Ctrl`, `Alt`, or `Win` arms that modifier for the next key, locks it on a quick second tap, or turns a locked one off. Each modifier tile shows which of its three states it is in, read from the engine, so a modifier that the console, a page swipe, or the idle code changes shows the same way as one that a tap changed. In milestone 1 the engine's only sink is the console key log, so nothing reaches the PC. A swipe that starts on a tile sends nothing and changes the page. A developer or the harness injects taps with `touch tap`, finds each tile with `ui tile <id>`, and reads the reports from the key record with `$TD serial keys`.

## Sub-features

- `fkey-tap` sends `keys_tap` with the tile's usage when a tap lifts inside the pressed tile. `f1` to `f12` send 58 to 69 in order. The record shows `kbd <mods> [<usage>]` and then `kbd 0 []`. A tile sends on release, never on press, so holding a tile sends once, at the lift.
- `fkey-mod` sends `keys_mod` for `shift`, `ctrl`, `alt`, and `win`. A modifier tile sends no report by itself. The modifier rides in the next key's report. The engine owns the transitions, so the page only forwards the tap.
- `fkey-look-off` draws a modifier tile that is `OFF` as any other tile, with the `tile` fill (6406) and no ring.
- `fkey-look-one-shot` draws a tile whose modifier is `ONE_SHOT` with a 4 px opaque ring in `glow` (19743), 2 px outside the tile. The tile's fill does not change. A key tap spends the modifier, and the ring goes out on the next frame.
- `fkey-look-locked` draws a tile whose modifier is `LOCKED` with the `mod_locked` fill (8984) and a lock glyph in `lock` (61311), a shackle over a body, at the right of the tile. The label stays in `text`. A locked tile keeps its look through a page swipe and a trip to `Media` and back.
- `fkey-follow-engine` makes the looks follow `keys_get_state()`, polled every 50 ms and read again right after a tile tap. `keys mod shift` from the console arms the ring within about 50 ms, and `keys clear all` clears every look the same way.
- `fkey-swipe-clears` calls `keys_clear_one_shot()` when the page changes, by a swipe or `ui goto`, and keeps locked modifiers. A swipe that bounces at the end does not change the page and clears nothing.
- `fkey-swipe-quiet` sends nothing for a press that starts on a tile and becomes a swipe, a sideways drag, or a vertical move. A tap in the gap between tiles sends nothing.
- `fkey-tile-box` answers `ui tile <id>` with `name` (the tile's label, `F5`), `page`, `x`, `y`, `w`, `h`, `cx`, and `cy`, and `ui state` reports `tile_count`, 16 on `F-Keys` and 6 on `Media`. The plan's `tiles` list did not fit one reply, so each lane reads the box it needs.

Tokens, as RGB565 decimals with hex and the PNG color they screenshot as: `glow` 19743 (`4D1F`, 74,162,255), `mod_locked` 8984 (`2318`, 33,97,198), `lock` 61311 (`EF7F`, 239,239,255), `tile` 6406 (`1906`, 24,32,49), `bg` 2114 (`0842`, 8,8,16). `r5=r8>>3`, `g6=g8>>2`, `b5=b8>>3` gives the RGB565 values back exactly.

## How to get to it (user POV)

- Tap a tile on the `F-Keys` page. Tap `Shift` once and then `F5` for Shift+F5. Tap `Ctrl` twice quickly to lock it, and once more to unlock it.
- Run `$TD serial cmd "ui tile f5"` for the tile's box, then `$TD serial cmd "touch tap <cx> <cy>"` to tap its centre. Run `$TD serial cmd "keys mod shift"` to arm a modifier from the console.
- Run `$TD serial keys --out <file>` to read the record, and `$TD serial capture --no-reset --send "keys log on" --send "touch tap <cx> <cy>"` when the `keys:` log lines are the evidence.

## Driving it with touchdeck.ps1

Preconditions:

- The build under test is M1-10 or later, and `$TD serial doctor` exits `0` with `build_matches` true.
- Evidence directory `E=<absolute path>/.verify/<YYYYMMDD-HHMMSS>-fkey-page` is new, and Doctor's JSON is saved there as `doctor.json`.
- Start each recipe on page 0 at rest with every modifier `OFF` and the record empty. Run `$TD serial cmd "keys clear all"` and `$TD serial cmd "ui goto 0"`, then `$TD serial cmd "ui state"` and require `page` 0, `animating` false, and an empty `pressed_tile`.
- Nobody touches the panel during an injection recipe.
- A recipe that reads the record runs `$TD serial cmd "keys record start"` first, `$TD serial cmd "keys record stop"` after, and then `$TD serial keys --out $E/<name>.json`, whose `brief` list reads each report as `kbd <mods> [<keys>]`.
- Aim each tap at the tile's `cx` and `cy` from `$TD serial cmd "ui tile <id>"`. On `F-Keys` the centres are `cx` 143, 389, 635, 881 by column, and `cy` 128, 248, 368, 488 by row, so `f5` is (143, 248), `shift` is (143, 488), and `ctrl` is (389, 488).
- Pixel reader, once per PowerShell session: `function px($f, $w, $x, $y) { $b = [IO.File]::ReadAllBytes($f); $o = ($y * $w + $x) * 2; $b[$o] + 256 * $b[$o + 1] }`. It reads a `--raw` screenshot. A ring probe set for a tile at (`x`, `y`, `w`, `h`) with centre (`cx`, `cy`) is (`x`-4, `cy`), (`cx`, `y`-4), (`x`+`w`+3, `cy`), and (`cx`, `y`+`h`+3). The lock probes are (`x`+`w`-31, `cy`-14) for the shackle and (`x`+`w`-31, `cy`+10) for the body. The fill probe is (`x`+12, `cy`), which no label covers.

- **A tap on F5 (lane 2).** Start the record, run `$TD serial cmd "touch tap 143 248" > $E/f5-tap.json`, run `$TD serial screenshot --out $E/f5.png --raw $E/f5.rgb565 > $E/f5.json`, stop the record, and run `$TD serial keys --out $E/f5-record.json`. `brief` is exactly `kbd 0 [62]`, `kbd 0 []`, with `count` 2 and `dropped` 0. View `$E/f5.png`. It shows `F-Keys`, sixteen tiles, and no ring or fill on any modifier tile.
- **The key log, both You-see items.** Run `$TD serial cmd "ui tile f5"` and `$TD serial cmd "ui tile shift"`, then `$TD serial capture --out $E/log --seconds 12 --no-reset --send "keys log on" --send "touch tap 143 248" --send "touch tap 143 488" --send "touch tap 143 248" --send "keys log off" --expect 'keys: \{"seq":\d+,"t":\d+,"type":"kbd","mods":0,"keys":\[62\]\}' --expect 'keys: \{"seq":\d+,"t":\d+,"type":"kbd","mods":0,"keys":\[\]\}' --expect 'keys: \{"seq":\d+,"t":\d+,"type":"kbd","mods":2,"keys":\[62\]\}' --expect 'keys: \{"seq":\d+,"t":\d+,"type":"kbd","mods":0,"keys":\[\]\}'`. Exit `0`. The first pair is F5 alone, and the second pair is Shift+F5, so the Shift tap rode on the next key. The log lines go through stdio, so the record is the proof when a count matters.
- **Shift armed, spent, and the next key plain (lane 4).** Start the record. Run `$TD serial cmd "touch tap 143 488"`, then `$TD serial screenshot --out $E/shift-armed.png --raw $E/shift-armed.rgb565`, then `$TD serial cmd "touch tap 143 248"`, then `$TD serial screenshot --out $E/shift-spent.png --raw $E/shift-spent.rgb565`, then `$TD serial cmd "touch tap 389 248"`, and run `$TD serial cmd "keys state" > $E/shift-state.json`. Stop the record and run `$TD serial keys --out $E/shift.json`. `brief` is `kbd 2 [62]`, `kbd 0 []`, `kbd 0 [63]`, `kbd 0 []`, and `shift` reads `OFF`. - **Ctrl locked with the lock glyph (lane 5).** Start the record. Run `$TD serial cmd "touch tap 389 488" --repeat 2`, then `$TD serial screenshot --out $E/ctrl-locked.png --raw $E/ctrl-locked.rgb565`, then `touch tap 143 248` and `touch tap 389 248`, and `keys state`. Stop the record and run `$TD serial keys --out $E/ctrl.json`. `brief` is `kbd 1 [62]`, `kbd 0 []`, `kbd 1 [63]`, `kbd 0 []`, and `ctrl` reads `LOCKED`. In `ctrl-locked.rgb565` the `ctrl` tile (x 274, y 436) reads 8984 at the fill probe, and 61311 at both lock probes, (473, 474) and (473, 498). View `$E/ctrl-locked.png`. `Ctrl` has a blue fill and a white padlock at its right, and no other tile changed. A `--repeat 2` pair can land more than 300 ms apart on a slow host, and the second tap then reads `OFF`. Run it again. Run `keys clear all` afterward.
- **Double-tap gap on the device clock.** Run `$TD serial capture --out $E/dtap --seconds 6 --no-reset --send "touch tap 389 488" --send "touch tap 389 488" --send "keys state"`. Both taps queue at once, so the gap is the shortest the console allows. In PowerShell, `$ms = Select-String -Path $E/dtap/serial.log -Pattern 'I \((\d+)\) ui: click taps=\d+ tile=ctrl' | ForEach-Object { [int]$_.Matches[0].Groups[1].Value }; $ms[1] - $ms[0]` prints the gap in milliseconds. The owner measured 116 against the engine's 300 limit, and `keys state` read `ctrl` `LOCKED`. The second `touch tap` waits for the frame that the first tap's release fade occupies, which is why its `deliver_us` was 62650 and the first one's was 3504. Run `keys clear all` afterward.

Run `$TD serial cmd "ui goto 0"` afterward.

- **F1 to F12 in order, written from the plan and not run by the owner (lane 3).** Tap the centres of `f1` to `f12` in order, 143 389 635 881 across at 128, 248, and 368. `brief` has 24 reports, the odd ones `kbd 0 [58]` to `kbd 0 [69]` in order, and every even one `kbd 0 []`.
- **The engine's console writes show on the tiles.** Run `$TD serial cmd "keys mod shift"`, wait 0.3 s, and take `$TD serial screenshot --out $E/console-shift.png --raw $E/console-shift.rgb565`. The `shift` ring probes read 19743. Run `$TD serial cmd "keys clear all"`, wait 0.3 s, and take a second screenshot. They read 2114.
- **The F-Keys tap time (perf).** Start the record. Run `$TD serial cmd "touch tap 143 248" --repeat 100 --interval 0.25 --time > $E/taps100.jsonl 2> $E/rtt100.txt`. In PowerShell, `$d = Get-Content $E/taps100.jsonl | ForEach-Object { ($_ | ConvertFrom-Json).deliver_us } | Sort-Object; $d[[int][math]::Ceiling(0.95 * $d.Count) - 1]` prints the p95 of `deliver_us` in microseconds, and the plan's bound is 60000. Spacing the taps 0.25 s apart matters, because a tap that lands inside the previous release fade waits one frame, about 65 ms. The owner's run had a p95 of 10980. Stop the record. `count` is 200 with `dropped` 0.
- **Frame rate with the looks on (perf).** Run `$TD serial cmd "perf fps 5" --timeout 8` idle, then after `touch tap 143 488` (Shift armed), then after `keys clear all` and `touch tap 389 488` twice (Ctrl locked), and run `keys clear all` last. The owner read 75 frames, 74 frames, and 75 frames in five seconds. The plan's M1-06 floor is 15 fps for a full redraw, so one frame in five seconds is the size of the noise.
- **Free internal RAM.** Run `$TD serial cmd "heap"`. The owner read `free_internal` 129771 at M1-10.

## Gotchas

- Nothing reaches the PC in milestone 1. A record entry proves that the engine emitted the report. A watcher on the PC would see nothing.
- A tap on an `F-Keys` tile now sends a key and may arm a modifier. The recipes of [UI pages](./ui-pages.md) tap `f1` and `f8` and swipe from tiles, so at M1-10 they also leave F1 reports in the record. A recipe that taps `shift`, `ctrl`, `alt`, or `win` leaves that modifier armed or locked, so run `keys clear all` between recipes. A reset clears them too.
- Settle before a look screenshot. The ring appears in one frame, and the fill and the pressed look fade over 120 ms. Each `$TD` call starts pwsh and activates ESP-IDF first, which takes seconds, so a screenshot in its own call is always settled. A screenshot that shares a serial session with the tap can land inside the fade.
- The ring sits outside the tile, in the gap between tiles, and the hit test is the tile's rectangle. A tap on the ring lands on the page, not the tile.
- The looks lag the engine by up to one 50 ms poll when something other than a tap changes it. The tile's own tap refreshes the looks at once.
- The deck's full redraw already runs at the 15 fps floor. Do not read a lower figure from a `perf fps` run that shared the session with a screenshot or another command.
- `ui tile` replies with `id` and `name`. `name` is the label, so `ui tile f5` has `"name":"F5"`.
- From M2-04 on, the F-Keys page comes from the built-in layout, `schema/examples/builtin.json`, and each tile runs its own `action`. A stored layout can put a tile named `shift` anywhere with any action, so read `ui tile <id>`'s `action` before you assume what a tile sends.
- `touch tap` replies after LVGL has taken the release and run one more read, and the key report leaves inside that window, so the record already holds a tap's reports when its reply arrives.
